# Deployment and acceptance

This repository is a local prototype, not a production deployment. Its source-scoped discovery, risk triage, reviewer authorization, evidence exports, and gated remediation need managed identity, AWS, database, worker, secret, network, backup, and monitoring acceptance at the **exact release revision**. See [evidence and risk](evidence-and-risk.md), [AI governance](ai-governance.md), and [Floci tests](floci.md) for their detailed contracts.

## Operating boundaries

| Area | Application safeguard | Deployment or acceptance still needed |
| --- | --- | --- |
| Discovery | IAM user/group, role/trust, and Identity Center assignment scopes publish independently. Incomplete/newer attempts block new campaigns and live remediation; old publication remains historical. Real IAM scans require `AWS_ACCOUNT_ID` and STS account verification. | Least-privilege read roles; live pagination/coverage and account checks. Boundaries, SCPs, resource/session policies, Identity Center member expansion, and effective access remain unassessed. |
| Risk/review | Append-only policy and grant assessments; campaigns pin eligible snapshots. Missing/unsupported evidence routes to manual review. Decisions require open campaign, pool and individual assignment, and no open exception. | Independently labeled IAM corpus; real reviewer workflow and buyer validation. A revoked path does not prove equivalent access gone. |
| Identity | API verifies OIDC signature, issuer, audience, expiry, subject, groups and account scope; missing/malformed scopes deny access. `sub` identifies actors. CLI decisions are `LOCAL_DEMO` on seeded `MOCK` pins only and cannot authorize remediation. | Managed OIDC, HTTPS JWKS, TLS gateway, WAF/rate limits, directory-backed reviewer lookup. Shared-environment assignment fails closed until directory membership verification exists. |
| AI | Default-off explanation and Q&A; minimized provider payload, versioned approval, immutable artifact provenance, per-turn Q&A authorization and telemetry. | Approved provider/data terms, real-provider quality study, daily request/spend limits, latency baseline and alarms, deployed kill switch/worker role. See [AI governance](ai-governance.md). |
| Data/audit | Ordered transactional migrations; immutable pins/events, scoped CSV/JSON/evidence/manifest exports with SHA-256, surfaced S3 upload failure. | Managed PostgreSQL TLS/backups, protected append-only audit/archive, S3 versioning/retention/KMS and least-privilege roles. |
| Runtime | Local Compose starts PostgreSQL, migrations, API, frontend, and Floci; frontend binds loopback and keeps tokens in server-side Auth.js/BFF session. Operations reports recorded jobs, not worker heartbeat. | Public TLS/domain, managed workers/scheduler, observability, alerts, secrets, recovery, and infrastructure deployment. Compose is not AWS staging. |

The discovery principal needs the IAM list/get calls used by the scanner, including users, groups, attached/inline policies, managed policy versions, roles/trust, and configured Identity Center reads. Keep its role separate from remediation credentials. A deployed AI worker should have SELECT on pinned evidence and write access only to AI jobs, attempts, and artifacts; deny it decision and remediation-table mutation. The repository does not provision these roles.

Configure `OIDC_ISSUER`, `OIDC_AUDIENCE`, `OIDC_JWKS_URL`, `OIDC_ACCOUNT_SCOPE_CLAIM`, group mappings, and frontend Auth.js credentials. Staging/production require account-scope configuration; `OIDC_ALLOW_GLOBAL_SCOPE` and `OIDC_ALLOW_UNVERIFIED_REVIEWER_ASSIGNMENTS` are local development opt-ins. Keep tokens and secrets out of logs and Git. Campaign deadlines are visible, but reminders/escalation remain operational work. Production live remediation is blocked in code.

## Staging remediation acceptance record

Only direct managed IAM **user** policy detachment (`DetachUserPolicy`) and direct inline user policy deletion (`DeleteUserPolicy`) have a live worker path. Group, role, trust, and Identity Center grants are ineligible. Approval and a verified direct-path removal never prove all effective access disappeared.

1. Use a dedicated staging AWS account and restricted remediation role. Record account, role, operator, independent approver, change ticket, user/policy target, and planned action. Grant only required IAM reads and target-specific detach/delete permissions.
2. Apply all migrations at the deployed revision to staging PostgreSQL. Confirm hosted PostgreSQL migration, concurrency, and evidence checks at that same revision. Complete real AWS discovery/risk assessment; confirm a fresh, complete published snapshot with no newer nonpublished attempt. Create a review pinned to its exact path.
3. Record `REVOKED` through the OIDC reviewer API. A different authenticated approver records an immutable approval bound to that decision. Legacy/projection-only approval is ineligible. Run `DRY_RUN=true`, inspect the exact candidate and allowlist, and confirm mandatory administrator/break-glass deny patterns.
4. Independently verify preflight user ID/ARN, attachment, policy hash/version, and action. Record `STAGING_REMEDIATION_ACCEPTANCE_ID` tied to the review and ticket. For this controlled run only set `MOCK_IAM=true`, `SEEDED_IAM=false`, `APP_ENV=staging`, matching `AWS_ACCOUNT_ID`, `DRY_RUN=false`, `ENABLE_REMEDIATION=true`, `ALLOW_LIVE_REMEDIATION=true`, and a nonempty exact `REMEDIATION_ALLOWLIST`.
5. Inspect `/reviews/{id}/remediation` and the export: `PREFLIGHT_PASSED → ACTION_REQUESTED → ACTION_VERIFIED`, approval event, fencing token, absent direct attachment, and `principal_access_status=not_evaluated`. Test changed policy, newer/failed scan, expired lease, concurrent worker, lost AWS response, and still-present attachment. Uncertainty must require read-only reconciliation and a **new** snapshot/review/approval, never an unapproved repeat action.

Record timestamp, revision, tests, account, review/decision/approval/action IDs, manifest hash, people, and disposition in the controlled change record. Remove live flags and acceptance ID afterward. The ID is an operator assertion, not proof that this procedure happened. Production needs a separate security and deployment decision; do not remove the code gate because staging passed.

## Historical local result and open acceptance

The **2026-11-03** pre-staging record reported 86 Python passes/9 skips, TypeScript/ESLint/build success, eight Vitest passes, five mocked Playwright role journeys with automated accessibility scans, and a clean diff check. It used test-only Auth.js sessions and mocked BFF responses. OIDC environment values were absent, so authenticated Compose, real identity-provider, multi-account, AWS, and directory-backed reviewer assignment were **not** tested. These counts describe that dated run only and must not be reused as current release evidence.

For a new release, collect local SQLite/PostgreSQL and frontend results, hosted CI at the exact commit, managed OIDC/API account isolation, AWS staging discovery and remediation where applicable, real provider evaluation where applicable, backups/recovery, monitoring, and an owner-approved go/no-go record. Image builds and Floci tests do not substitute for those checks.
